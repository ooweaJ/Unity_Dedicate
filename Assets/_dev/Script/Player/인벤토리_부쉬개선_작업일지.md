## 1️⃣ 장착된 장비 인벤토리 표시 버그 수정

### ✅ 결과

장착 중인 장비 인스턴스가 인벤토리 장비 탭에 더 이상 표시되지 않음

### 📌 수행 이유

장비는 `user_items_equipment` 테이블에 인스턴스 단위로 존재하고, 장착 정보는 별도 `equipped_items` 테이블에 저장된다. 서버가 전체 `user_items_equipment`를 그대로 반환하면 장착 중인 장비도 포함되어 인벤토리에 중복 노출됨.

### 📝 작업 내용

`userService.js`의 `fetchFullUserData()` 쿼리에 서브쿼리로 장착 중인 인스턴스를 제외

### ⚠️ 트러블슈팅

- **문제:** 장비를 장착해도 인벤토리 장비 탭에 아이콘이 그대로 남아 있음
    - **원인:** `fetchFullUserData`가 `user_items_equipment` 전체를 조회. `equipped_items` 테이블과 JOIN 또는 필터링 없이 반환
    - **해결 방법:** `NOT IN (SELECT equip_instance_id FROM equipped_items WHERE user_id = ?)` 서브쿼리 추가

    **🧠 내가 이해한 원리:**
    장비 인스턴스 보관 테이블과 장착 정보 테이블을 분리한 인스턴스 기반 설계에서, "보유 = 전체 - 장착 중"이라는 관계를 쿼리 단에서 명시해야 한다.

### 💻 주요 코드 스니펫

**🔹 목적: 장착 중인 장비 제외 쿼리**

```javascript
// userService.js — fetchFullUserData()
const [equipment] = await db.query(
    `SELECT id AS equip_instance_id, item_id, enhance
     FROM user_items_equipment
     WHERE user_id = ?
       AND id NOT IN (SELECT equip_instance_id FROM equipped_items WHERE user_id = ?)`,
    [userId, userId]
);
```

📌 **사용 이유:** 서버 응답 단에서 필터링하면 클라이언트 코드 변경 없이 모든 API 호출에 일괄 적용됨.

📌 **주의할 점:** 서브쿼리에도 `user_id = ?` 조건을 추가해야 함. 없으면 다른 유저의 장착 데이터가 섞여 잘못된 필터링 발생.

## 2️⃣ 아이템 ID 충돌 버그 수정 (ItemType 기반 이벤트 분리)

### ✅ 결과

`equip_instance_id`와 `itemId`가 같은 숫자여도 올바른 정보 패널과 액션이 동작함

### 📌 수행 이유

`InventoryUI`가 클릭/hover 이벤트에 정수 ID 하나만 전달했다. 장비 탭의 slot ID는 `equip_instance_id`, 소모품 탭의 slot ID는 `itemId`인데 두 공간이 겹칠 수 있음. ID=1인 장비 인스턴스가 있으면 ID=1 소모품 hover가 장비 정보를 표시하는 버그.

### 📝 작업 내용

| 파일 | 변경 내용 |
|---|---|
| `InventoryUI.cs` | `OnItemClicked`, `OnItemHoverEnter`, `OnItemDragBegin` 이벤트 시그니처에 `ItemType` 추가 |
| `InventoryUIManager.cs` | 핸들러 3개(hover/click/drag) 모두 `ItemType` 파라미터 추가, 타입별 분기 처리 |

### ⚠️ 트러블슈팅

- **문제:** 소형 경험치 물약(itemId=1) hover 시 장비 인스턴스(equip_instance_id=1)의 정보가 표시됨
    - **원인:** `HandleItemHoverEnter`가 `_cachedEquipmentDatas`를 먼저 검색. ID 공간이 분리되어 있지 않아 우연히 같은 숫자가 매칭됨
    - **해결 방법:** 이벤트 발화 시 `targetType`(해당 `InventoryUI`의 아이템 타입)을 함께 전달. 핸들러에서 `sourceType`으로 먼저 분기한 뒤 해당 캐시만 검색

    **🧠 내가 이해한 원리:**
    서로 다른 의미를 가진 정수 ID를 같은 이벤트 채널에서 구분 없이 쓰면 공간 충돌이 생긴다. 이벤트에 출처 컨텍스트(타입 정보)를 함께 실어 보내는 것이 근본 해결책.

### 💻 주요 코드 스니펫

**🔹 목적: 이벤트에 ItemType 태깅**

```csharp
// InventoryUI.cs
public event Action<int, Vector2, ItemType> OnItemClicked;
public event Action<int, Vector2, ItemType> OnItemHoverEnter;
public event Action<int, ItemType>          OnItemDragBegin;

private void HandleSlotClicked(int id, Vector2 pos)    => OnItemClicked?.Invoke(id, pos, targetType);
private void HandleSlotHoverEnter(int id, Vector2 pos) => OnItemHoverEnter?.Invoke(id, pos, targetType);
private void HandleSlotDragBegin(int id)               => OnItemDragBegin?.Invoke(id, targetType);
```

**🔹 목적: 타입 기반 핸들러 분기**


📌 **사용 이유:** ID 공간이 다른 슬롯들이 같은 이벤트 버스를 공유할 때, 타입 태그가 라우터 역할을 함.

📌 **주의할 점:** `OnDisable`에서 `-=` 해제도 동일한 시그니처여야 제대로 해제됨. 메서드 그룹 참조를 쓰면 시그니처가 자동으로 맞음.

## 3️⃣ ItemInfoPanel 및 장비 클릭 흐름 개선

### ✅ 결과

- 장비 hover: `아이템명 +N`, 강화 배율 적용된 공격력/방어력 수치 표시
- 장비 클릭: "강화" 버튼 팝업 → 확인 시 강화 진행 (기존: 클릭 즉시 강화)
- 초월 조각 hover: 이름 + 보유 수량만 표시 (설명 불필요)

> 📸 **[스크린샷 추천]** +3 강화된 장비 hover 시 InfoPanel — "공격력 +130" 등 강화 수치 확인

### 📌 수행 이유

기존 `SetData(ItemRawData, int amount)`는 두 번째 인자를 항상 "보유 수량"으로 표시. 장비는 `amount` 자리에 `enhance` 값이 들어와 "보유 수량: 3" 같은 잘못된 표시가 나왔음.

장비 클릭 즉시 강화는 오조작 위험이 있고, 소모품처럼 액션 팝업을 거쳐야 UX가 일관적.

### 📝 작업 내용

| 파일 | 변경 내용 |
|---|---|
| `ItemTableSO.cs` | `ItemActionType.Enhance` 추가 |
| `ItemInfoPanel.cs` | `SetEquipmentData(ItemRawData, int enhance)` 메서드 추가 |
| `ItemInfoPanel.cs` | `SetShardData`에서 description 제거 |
| `InventoryUIManager.cs` | 장비 hover → `SetEquipmentData` 호출 |
| `InventoryUIManager.cs` | 장비 클릭 → "강화" 액션이 담긴 팝업 표시 |

### 💻 주요 코드 스니펫

**🔹 목적: 강화 수치 반영 스탯 표시**

```csharp
// ItemInfoPanel.cs
public void SetEquipmentData(ItemRawData staticData, int enhance)
{
    txtName.text = enhance > 0 ? $"{staticData.displayName} +{enhance}" : staticData.displayName;
    txtDescription.text = staticData.description;

    float mult = 1f + enhance * 0.1f;
    int atk = Mathf.RoundToInt(staticData.atkBonus * mult);
    int def = Mathf.RoundToInt(staticData.defBonus * mult);

    var sb = new StringBuilder();
    if (atk > 0) sb.AppendLine($"공격력 +{atk}");
    if (def > 0) sb.AppendLine($"방어력 +{def}");
    txtAmount.text = sb.Length > 0 ? sb.ToString().TrimEnd() : "-";
}
```

📌 **사용 이유:** 강화 1단계당 10% 배율 증가. 스탯 표시에 현재 강화 배율을 반영해 플레이어가 강화 효과를 바로 확인할 수 있음.

**🔹 목적: 장비 클릭 → 강화 팝업**

## 4️⃣ 부쉬 반투명 효과 구현

### ✅ 결과

- 로컬 플레이어가 부쉬에 진입하면 자신의 캐릭터와 부쉬 메쉬 모두 반투명 전환 (alpha 0.4 / 0.35)
- 부쉬 이탈 시 원본 머티리얼 복원
- URP / Standard 렌더 파이프라인 양쪽 지원

> 🎬 **[영상 추천]** 부쉬 진입 후 캐릭터+부쉬 반투명 → 이탈 후 불투명 복원 전체 흐름
> 📸 **[스크린샷 추천]** 부쉬 안 캐릭터 반투명 상태 / 적 시점에서는 안 보이는 상태 비교

### 📌 수행 이유

기존 `SetVisible(bool)`은 `renderer.enabled` 토글만 사용. 자신의 캐릭터가 부쉬 진입 시 완전히 보이거나 숨어있는 것처럼 보여 어색함. 실제 게임(브롤스타즈 등)처럼 자신은 반투명으로 "숨어있음"을 인지하게 해야 함.

### 📝 작업 내용

- `CacheRenderers` 호출 시 원본 머티리얼 배열(`_originalMats`)과 fade 복사본(`_fadeMats`) 미리 생성
- `SetVisible`에서 `visible=true && inBush=true`이면 `_fadeMats`로 교체
- `OnCurrentBushChanged`에서 로컬 플레이어일 때 `BushZone.SetLocalPlayerInside()` 호출해 부쉬 메쉬도 반투명 전환
- `OnDestroy`에서 동적 생성한 fade 머티리얼 메모리 해제

### ⚠️ 트러블슈팅

- **문제:** `renderer.material.color.a`만 바꿔도 반투명이 안 됨
    - **원인:** Opaque 모드 머티리얼은 알파값을 무시함. 투명 렌더링을 위해 렌더 모드(Standard: `_Mode`, URP: `_Surface`) 를 Transparent로 전환해야 함
    - **해결 방법:** 머티리얼 복사본 생성 시 셰이더 키워드와 renderQueue를 코드에서 직접 설정. URP / Standard 를 `HasProperty`로 판별해 분기 처리

    **🧠 내가 이해한 원리:**
    Unity 머티리얼의 투명 여부는 색상 알파값이 아니라 셰이더의 렌더 모드가 결정한다. `_Mode=2` (Fade) 또는 `_Surface=1` (Transparent)로 설정해야 알파가 실제 렌더링에 반영된다.

### 💻 주요 코드 스니펫

**🔹 목적: 런타임 fade 머티리얼 생성 (URP/Standard 대응)**

```csharp
// PlayerBushState.cs
public static Material CreateFadeMaterial(Material src, float alpha)
{
    var mat = new Material(src);

    if (mat.HasProperty("_Surface"))       // URP
    {
        mat.SetFloat("_Surface", 1f);
        mat.SetFloat("_ZWrite",  0f);
        mat.EnableKeyword("_SURFACE_TYPE_TRANSPARENT");
        mat.renderQueue = (int)RenderQueue.Transparent;
    }
    else if (mat.HasProperty("_Mode"))     // Standard
    {
        mat.SetFloat("_Mode",   2f);
        mat.SetInt("_SrcBlend", (int)BlendMode.SrcAlpha);
        mat.SetInt("_DstBlend", (int)BlendMode.OneMinusSrcAlpha);
        mat.SetInt("_ZWrite",   0);
        mat.EnableKeyword("_ALPHABLEND_ON");
        mat.renderQueue = 3000;
    }

    if (mat.HasProperty("_BaseColor")) { var c = mat.GetColor("_BaseColor"); c.a = alpha; mat.SetColor("_BaseColor", c); }
    else                               { var c = mat.color;                  c.a = alpha; mat.color = c; }
    return mat;
}
```

📌 **사용 이유:** `CacheRenderers` 시점에 미리 생성해두면 매 프레임 머티리얼 생성 비용이 없음. 진입/이탈 시 배열 교체만으로 동작.

📌 **주의할 점:** `renderer.materials = array` 는 항상 새 인스턴스를 만들지만, `renderer.sharedMaterials = array` 는 공유 머티리얼을 그대로 참조함. 복원 시 `sharedMaterials`로 설정해야 불필요한 인스턴스 생성을 막을 수 있음.

## 5️⃣ 부쉬 내 투사체 발사 불가 버그 수정 + 레이어 시스템 도입

### ✅ 결과

부쉬 안에서 투사체가 정상 발사됨. `hitLayers` 마스크로 투사체가 충돌할 레이어를 인스펙터에서 지정 가능

> 🎬 **[영상 추천]** 부쉬 안에서 발사 → 외부 적 명중 장면

### 📌 수행 이유

투사체가 부쉬 안에서 스폰되자마자 사라지는 현상 발생. 기존 코드는 `isTrigger` 체크만 있었고 Plane(바닥)이나 부쉬의 non-trigger 물리 콜라이더에 즉시 충돌해 `DestroySelf()` 호출됨.

특정 컴포넌트를 코드에서 하드코딩으로 필터링하는 것은 임시방편이고, 레이어 기반 관리가 유지보수에 맞는 정석.

### 📝 작업 내용

디버그 로그로 충돌 대상 확인 (`Plane`에 충돌 확인) → `ProjectileBase`에 `hitLayers` LayerMask 필드 추가, 해당 레이어가 아닌 충돌은 무시

### ⚠️ 트러블슈팅

- **문제:** 부쉬 밖에서는 투사체 발사 정상, 부쉬 안에서만 즉시 소멸
    - **원인:** 부쉬 안에서 스폰 위치(`origin + Vector3.up * 0.5f`)가 Plane의 MeshCollider 범위 안이었음. 투사체(trigger)가 Plane(non-trigger)과 즉시 `OnTriggerEnter` → `DestroySelf()`
    - **해결 방법:** `ProjectileBase`에 `hitLayers` LayerMask 추가. `(hitLayers & (1 << other.gameObject.layer)) == 0` 조건으로 대상 레이어가 아니면 즉시 리턴. Plane을 `Ground` 레이어에 배치하고 투사체 `hitLayers`에서 제외

    **🧠 내가 이해한 원리:**
    Unity 물리 트리거는 레이어와 무관하게 겹치면 이벤트를 발생시킨다. "투사체가 무엇에 반응해야 하는가"를 코드 레벨에서도 명시적으로 지정해야 의도치 않은 충돌을 막을 수 있다. Physics Layer Collision Matrix는 엔진 레벨 필터, `hitLayers`는 코드 레벨 필터 — 이중 보호가 가능하다.

### 💻 주요 코드 스니펫

**🔹 목적: 레이어 기반 충돌 필터링**

```csharp
// ProjectileBase.cs
[Header("충돌 레이어")]
[SerializeField] private LayerMask hitLayers = ~0; // 인스펙터에서 Player, Obstacle만 체크

private void OnTriggerEnter(Collider other)
{
    if (!isServer) return;
    if (other.isTrigger) return;
    if ((hitLayers & (1 << other.gameObject.layer)) == 0) return; // 지정 레이어 외 무시
    if (owner != null && other.transform.root.gameObject == owner) return;

    HandleTriggerEnter(other);
}
```

📌 **사용 이유:** `CharacterWeapon`의 `data.targetLayer`와 동일한 방식으로 일관성 유지. 프리팹별로 충돌 레이어를 다르게 설정 가능(관통 투사체, 구조물만 파괴하는 투사체 등).

📌 **주의할 점:** 기본값 `~0`은 모든 레이어 허용(All). 반드시 프리팹 인스펙터에서 `Player`, `Obstacle`만 체크하도록 설정해야 함.

**추천 레이어 구성**

| 레이어 | 적용 오브젝트 | 투사체 hitLayers 포함 여부 |
|---|---|---|
| `Ground` | Plane, Terrain | ❌ |
| `Bush` | BushZone 오브젝트 | ❌ |
| `Player` | 플레이어 히트박스 | ✅ |
| `Obstacle` | 벽, 장애물 | ✅ |
| `Projectile` | 투사체 자신 | ❌ |

## 🧠 오늘 배운 점

- 인스턴스 기반 장비 설계에서 "보유 목록 = 전체 - 장착 중" 관계는 DB 쿼리 단에서 명시적으로 표현해야 한다
- 같은 이벤트 채널에서 출처가 다른 ID를 구분할 땐 ID 하나만 전달하면 충돌 위험이 있다 — 이벤트에 컨텍스트(타입)를 함께 태깅하는 것이 근본 해결책
- Unity 머티리얼 투명도는 color.a만으로는 안 됨. Opaque 셰이더는 알파를 무시하므로 렌더 모드 자체를 Transparent/Fade로 바꿔야 시각적으로 반영됨
- `renderer.materials` (인스턴스 배열)과 `renderer.sharedMaterials` (공유 참조)의 차이: 복원할 때 sharedMaterials를 써야 불필요한 머티리얼 인스턴스가 생성되지 않음
- 투사체 충돌 필터링은 `isTrigger` 체크만으로 부족하다. 레이어 기반 `hitLayers` 마스크로 "무엇에 반응하는가"를 명시해야 의도치 않은 충돌을 차단할 수 있다
